**Alcance:** análisis estático y documental; no autoriza ni ejecuta operaciones RF.

## 1. Propósito y criterio de evidencia

Este documento separa dos preguntas que la matriz canónica no debe comprimir en un solo estado:

1. **¿Qué se observó o reportó históricamente?**
2. **¿Qué prueba significativa puede ejecutarse hoy con la implementación y prerrequisitos disponibles?**

Un reporte técnico narrativo es evidencia válida de la observación que documenta. La ausencia de stdout, JSONL o captura no borra un resultado reportado, pero limita la inspección independiente, la reproducción exacta y las inferencias causales. Por ello se usan seis clases:

| Clase | Qué puede sostener |
|---|---|
| Registro experimental primario | Salida, captura, log, medición estructurada o registro contemporáneo directamente inspeccionable |
| Reporte experimental documentado | Condiciones, procedimiento, observaciones o conteos que acreditan lo reportado, aunque no incluya toda la salida cruda |
| Resumen experimental consolidado | Síntesis posterior trazable a experimentos identificables; conserva su alcance original |
| Claim histórico de implementación | README, commit o comentario con un resultado sin contexto experimental suficiente; se conserva como claim, no como reporte equivalente |
| Evidencia estática | Presencia, ausencia o contrato establecidos por source/SDK; no demuestra ejecución física |
| Medición física independiente | Frecuencia, potencia, espectro, modulación, switch o interoperabilidad observados con instrumento/peer apropiado |

Las categorías de readiness tampoco son resultados PASS/FAIL:

| Decisión | Significado |
|---|---|
| READY | Existe una prueba estrecha y significativa con implementación y prerrequisitos ordinarios actuales |
| CONDITIONAL | La prueba es significativa, pero exige autorización, setup, recuperación, peer o instrumento específicos |
| BLOCKED BY IMPLEMENTATION | Falta una función necesaria de firmware/API/protocolo o packaging mantenible |
| BLOCKED BY HARDWARE | La configuración física del target no está establecida como compatible |
| UNSUPPORTED BY DRIVER CONTRACT | El comando TI seleccionado no puede expresar el comportamiento solicitado |
| NOT APPLICABLE | La prueba propuesta no puede validar el claim pretendido; debe cambiarse la pregunta |
| INSUFFICIENT INFORMATION | La evidencia disponible no establece causa, omisión o factibilidad |

## 3. MIOTY por niveles de prueba

### Nivel A — API/configuración

La implementación actual puede serializar y aceptar `mioty_868_tsunb` mediante `Radio.configure_prop()` y `SET_PROP_CONFIG`. [`smoke_prop_phase1.py`](../python/examples/smoke_prop_phase1.py) puede ejercer ese camino. Esto sólo comprobaría serialización, ACK y ausencia de error inmediato; como `RadioIF_setPropConfig()` retorna `void` y no hay readback, no demuestra parámetros efectivos ni MIOTY. El valor incremental frente a la inspección estática es bajo, pero puede servir como regresión de control.

### Nivel B — paquete FSK genérico

Dos boards pueden intentar un marker con la misma configuración usando [`smoke_ota_txrx.py`](../python/examples/smoke_ota_txrx.py) y `--preset mioty_868_tsunb`. La pregunta válida sería: **¿el backend packet FSK actual entrega bytes entre dos FeralRF a la tasa/desviación nominal solicitadas?** No sería una prueba TS-UNB.

Prerrequisitos: ruta/antenas 868 confirmadas, build identificado, band control explícito, entorno autorizado, RX primero, marker único, cleanup y preferiblemente analizador para distinguir configuración solicitada de señal efectiva. El histórico 0/10 no prueba incompatibilidad; su causa no está establecida. Repetir Nivel B sólo se recomienda si la factibilidad del backend lento es una decisión de desarrollo, no para “validar MIOTY”.

### Nivel C — TS-UNB físico/protocolario

No es ejecutable con el firmware actual. Faltan, como mínimo, telegram splitting, coding/interleaving, scheduling y distribución temporal/frecuencial de sub-ráfagas, formato/procedimientos y recepción/reensamble. El sync genérico `0x930B51DE` y packet mode TI no sustituyen esas funciones. Se requieren prototipo offline con vectores, decisión de patch/backend TI y luego instrumentación.

### Nivel D — interoperabilidad MIOTY

También está bloqueado. Exige la implementación del nivel C, un rol/modo definido y una base station o peer MIOTY independiente. La aceptación debe usar telegramas válidos y procedimientos del rol, no marcadores FeralRF.

**Siguiente paso recomendado:** estudio go/no-go y prototipo offline. Nivel B es opcional y estrecho; no es un prerequisito suficiente ni una prueba de MIOTY.

## 4. OOK 868: procedimiento controlado reconstruible

El reporte histórico 10/10 se conserva como observación reportada. RF-05 sigue siendo necesario sólo para repetición sobre la revisión/build actual y para validar recuperación segura.

No existe en este checkout `experimental_artifacts/next_rf_validation/rf05_ook_868.py`. El runner genérico [`smoke_ota_txrx.py`](../python/examples/smoke_ota_txrx.py) puede entregar markers, pero no exige power-cycle, identidad Shell ni control post-OOK. [`smoke_prop_phase1.py`](../python/examples/smoke_prop_phase1.py) usa `--auto-reset`, mecanismo insuficiente para garantizar descarga de patches. Por tanto, no hay un script standalone listo que implemente el experimento compuesto.

Una futura ejecución autorizada debe:

1. Identificar dos placas, Bridge/Shell y build sin aritmética de puertos.
2. Confirmar ruta/antena 868, entorno autorizado y posibilidad de retirar toda alimentación.
3. Realizar power-cycle total inicial y un control FSK/GFSK 868 con cleanup.
4. Configurar OOK una sola vez, iniciar RX antes de diez TX con marker único y registrar ACK, errores, paquetes y stats.
5. No cambiar PHY, frecuencia o preset después de cargar OOK.
6. Cerrar handles; ante cualquier cleanup ambiguo, no continuar en caliente.
7. Retirar alimentación completamente y ejecutar un control IEEE fresco tras reconexión.

La recepción OOK raw y la recuperación posterior forman un resultado compuesto. Un PASS OTA sin control post-power-cycle sólo sería PARTIAL. La prueba no mide profundidad OOK, espectro, potencia ni interoperabilidad con un dispositivo OOK externo.

### 5.1 Contratos CLI y cleanup verificados estáticamente

- `smoke_ota_txrx.py` exige `--tx-port` y `--rx-port`, más `--phy` o `--preset`; acepta `--channel`, `--power`, `--count` y `--min-markers`. Devuelve 0 por umbral de markers, 1 por umbral incumplido, 2 por falta de PHY/preset y 4 por excepción. Ejecuta `RX_STOP`, pero suprime su excepción; además deriva Shell como puerto `+2`. Por ello su PASS no acredita cleanup ni reset correctos.
- `smoke_prop_phase1.py` acepta `--port`, `--preset`, `--power`, `--duration`, `--tx-timeout`, `--packet-hex`, `--min-packets` y `--auto-reset`. Es un smoke de un board: prueba ACK/RX local/TX ACK, no entrega OTA. Sus códigos 2–7 separan entrada, conexión, timeout, protocolo, excepción y umbral; `--auto-reset` llama `reset_device()`, no garantiza un power-cycle total y hereda la asociación Shell insegura.
- `smoke_f25_crypto.py` acepta `--port`, ejecuta nueve pruebas y devuelve 0 sólo si 9/9 pasan, 1 en caso contrario; desconecta en `finally`. Importa `cryptography` al iniciar, por lo que la dependencia debe comprobarse sin asumir instalación.
- `smoke_f17_emulation.py` exige `--tx-port`/`--rx-port`, admite `--count`, `--skip-ook` y `--skip-433`, y devuelve 0 sólo si todas las personalidades seleccionadas superan su umbral. Su reset `+2`, el `RX_STOP` con excepción suprimida, 10 dBm fijo en Sub-GHz y la mezcla de rutas condicionadas impiden usarlo sin recorte y revisión.
- El `killerbee_sniff.py` del working tree acepta `--port`, `--channel`, `--count`, `--timeout`, `--pcap`, `--duration` y `--min-valid-crc`; exige puerto explícito, canales 11–26, distingue BLOCKED/FAIL y hace `sniffer_off()`/`close()`. Su contrato es adecuado para captura pasiva, pero RF-04 no puede declararse READY hasta resolver packaging; el archivo tiene una modificación local preexistente.
- `demo_mioty_listen.py` exige `--port` y admite preset/duración/hex; termina con código 0 aunque no reciba paquetes y sólo desconecta, sin `stop_rx()` explícito. Los demos Wi-SUN/Sidewalk son equivalentes en alcance. Ninguno es un criterio de aceptación protocolario.
- `smoke_jam_phase1.py` valida rangos y códigos de ACK/errores, intenta `stop_jam()` en `finally`, pero usa 20 dBm por defecto y no observa energía ni efecto. `smoke_f22_tx_test.py` sólo acepta `--tx-port`/`--rx-port`, mezcla ACKs con un proxy de interferencia y devuelve 0 si cinco checks internos pasan; tampoco sustituye instrumentación.

## 6. Decisiones de cobertura

- **Ya existe cobertura histórica válida reportada:** BLE PHY raw, OOK 868 raw, crypto, emulación raw y varios resultados 433/2440, con limitaciones de inspección/reproducción.
- **Ya existe cobertura reciente raw:** IEEE, FSK/GFSK 868–915, W-MBus S/T/C nominal, Wi-SUN nominal y Sidewalk FSK nominal. No se justifica repetirlos para reclamar protocolos.
- **Genuinamente no ejecutado al nivel pretendido:** TS-UNB/MIOTY, interoperabilidad W-MBus/Wi-SUN/Sidewalk/Zigbee/Thread, spectrum, caracterización física CW/PRBS/potencia/switch, RF-05 reciente y KillerBee HIL.
- **No debe probarse con el contrato actual:** proprietary 2.4, 169 MHz y MSK/4-FSK/4-GFSK.
- **Requiere primero observabilidad/corrección:** completion TX y regresión completa `RX_STOP`/switching.
