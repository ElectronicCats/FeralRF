# F9 — partial fix note (Sub1G→BLE green, IEEE→BLE deferred)

**Date:** 2026-04-28
**Branch:** `feature/f9-868-to-ble-switch`
**Outcome:** ⚠️ **partial** — one of two PHY-back-to-BLE switch directions fixed.

## What was fixed

`Sub-1GHz 868 MHz → BLE 1M` switch now works without device reset. Test:

```
BLE baseline:    200 pkts (env scan ch37, 2 s)
Sub1G:             0 pkts (no env, expected)
BLE-after-Sub1G: 179 pkts ✅  (was 0 pre-fix)
```

## What's still broken

`IEEE 802.15.4 → BLE 1M` switch returns 0 pkts. The validation matrix
`BLE→IEEE→Sub1G→IEEE→Sub1G→BLE` cycle from the v2 design spec § F9 still
fails on the final BLE step because IEEE→BLE is broken regardless of how
many intermediate Sub1G steps happen.

## Root cause hypothesis (verified for Sub1G, partial for IEEE)

The TI RF driver in SDK 8.30 leaves `RF_core.init` flagged when at least
one client is open. Our code keeps a persistent 433 MHz boot handle
(`s_433_handle`) open for the firmware's lifetime, so when we
`RF_close + RF_open` to switch from a non-433 mode to another non-433
mode, the driver sees `RF_core` is "still initialized" and skips reloading
CPE patches for the new mode.

For Sub-1GHz → BLE, a 200 ms post-close settle is enough for the driver's
internal state machine to clear the init flag and reload the BLE bt5
patches on the next `RF_open`. For IEEE → BLE, the same delay does
**not** work — IEEE specifically leaves the RF core in a state that BLE
patches can't recover from even with a long settle.

## What was tried for IEEE→BLE

- 50 ms delay post-close: no effect
- 200 ms delay post-close: no effect
- 1 s delay post-close: not tried but likely same
- Drain ALL clients (close 433 boot handle too): **regressed Sub1G→BLE**
  (now both directions fail), so the persistent 433 client is somehow
  *helping* BLE patch reload after Sub1G but not after IEEE
- Per TI's `rfDiagnostics` example: their pattern is exactly RF_yield +
  RF_close + RF_open with one rfObject and no persistent handle. We
  have two RF_Objects (s_rf_object + s_433_rf_object) and one is always
  open. Eliminating that asymmetry would mean a larger refactor.

## What to try next session

1. **Instrument firmware with RF_core register dumps** before/after
   IEEE-close and BLE-open to see exactly which RF_core state survives.
   Likely candidates: frame filter PAN ID/short address registers, MAC
   address recognition, IEEE-specific seqStat or CRC seed in CPE RAM.
2. **Power-cycle the RF_core via PRCM register** (PRCM_PERIPH_RFC reset)
   between close and open. Heavy hammer but mirrors what the device-reset
   workaround does internally — without losing the host UART connection.
3. **Switch to one rfObject** (eliminate `s_433_rf_object`). 433 path
   would close+open like everyone else. Risk: 433 timing/init
   sensitivity that motivated the persistent handle in the first place.
4. **Check if `CMD_IEEE_RADIO_SETUP`'s frameFiltConfig** leaves IEEE-mode
   state in CPE that breaks BLE. Possibly clearing it before close
   helps.

## Acceptance for this commit

The partial fix is shipped because Sub-1GHz→BLE is a real improvement
that didn't exist before — the validation script's existing
"reset between tests" pattern still works for IEEE→BLE, so production
flow isn't blocked. The full 6/6 cycle without reset (the F9 close
criterion) is **not** met; F9 remains open.
