# Sony WH-CH720N — BLE forensics

**Date:** 2026-05-01
**Hardware:** CatSniffer #1 (CC1352P7) on `/dev/ttyACM2`, firmware = `feature/ti-rtos-migration` HEAD `afb15f5` (post v2.0-f12)
**Target:** Sony WH-CH720N headphones, MAC `A8:E6:E8:8A:7D:F8` (public, OUI Sony Corp)

## Why

Sandbox session against a real commercial BLE peripheral now that two BLE
devices are on hand (Sony WH-CH720N + Anker Soundcore — Soundcore not seen
on BLE so probably needs pairing mode). Validates F12 active scan + the
GATT path from `feature/ti-rtos-migration`.

## TL;DR

Sony WH-CH720N is a **rebranded Airoha SoC**. DIS strings are the Airoha
SDK example defaults — Sony didn't bother customizing them. BLE adv carries
a static 6-byte device descriptor only; all dynamic state is exposed via
GATT (Sony custom services) or via Bluetooth Classic.

GATT discovery from FeralRF works end-to-end on this peripheral. 12
services and 50+ characteristics enumerated cleanly. Standard DIS reads
return printable strings. Two DIS reads fail (`Reg Cert Data` timeout,
`PnP ID` GATT_READ failed) — non-blocking.

## BLE advertisement

```
ADV       (always, 1 unique variant)
  Flags                    = 0x18  → LE General Discoverable + BR/EDR Not Supported
  Complete UUIDs 16-bit    = 0xFE03  (Sony Headphones service)

SCAN_RSP  (always, 1 unique variant)
  Complete Local Name      = "WH-CH720N"
  Mfg 0xC0EA (Sony)        = 9e 27 50 10 fc 2f   ← STATIC across all observed states
```

90-second watcher session triggered: idle → connect to phone → idle →
disconnect → idle → NC button toggle → idle. The 6 mfg bytes never
changed; only RSSI varied with motion. Conclusion: the BLE adv mfg
payload is a fixed device descriptor, not a state indicator. State info
flows over BR/EDR and over GATT, not over BLE adv.

The 6 bytes have not been decoded against an authoritative source. Likely
structure (informed guess): `9E 27` header / signature, `50 10` model code
(LE → 0x1050), `FC 2F` capability flags. Confirmation requires a Sony
firmware reverse or a packet capture from another model in the same family.

## Characteristics summary (50+)

Full table in the script output — only highlights here:

- Sony 0xFE03 service: 1 char (handle 209, write-only, value 210). Likely a command point.
- Google Fast Pair (0xFE2C):
  - 258 R   Model ID                       (24-bit Sony product ID)
  - 260 W,N Key-based Pairing
  - 263 W,N Passkey
  - 266 W   Account Key
  - 269 W,N Beacon Actions
  - 272 R,W,N Additional Data
- Sony app protocol family (`5b833eXX`) — three near-identical instances, each with W + N chars.
- Airoha custom services have the standard Airoha char layout: a R/W command-control char + N event-out char.

## Step 1 — Fast Pair Model ID read

Handle 258 (`fe2c1233...`) returned **empty**. Cause: the FE2C service data
in the BLE adv shows leading byte `0x00` = Fast Pair non-discoverable
mode (this device has been paired with a Google account previously). In
non-discoverable mode the Model ID is replaced by an Account Key Filter
ciphertext, and the GATT char is not populated either. To extract the
Model ID via BLE you'd need to factory-reset the WH-CH720N to re-enter
discoverable mode. Not pursued — Sony WH-CH720N's Fast Pair Model ID is
public in Google's Nearby Devices registry.

## Step 2 — Custom R characteristics

```
h  9 GAP   0x2AA6  Central Addr Resolution           00         (not supported)
h154 Sony  91c10d9c::eea2e8a0...a52632                (empty)
h170 Sony  67a846ad::753eed35...2dc142     [N]        00 00
h181 Sony  55f80aef::c6b2f38c...0bbd5d7   [W]         (empty)
h186 Sony  55f80aef::3adf41af...88d5bf8d  [N]         00 00
h194 Sony  91c10d9c::99d1064e...d1a1f1    [W,N]       00 00
h212 Sony  0xFE03   ::2beea05b...82420b   [N]         GATT_READ done without value
h258 FP    0xFE2C   ::fe2c1233 Model ID               (empty)   (see step 1)
h272 FP    0xFE2C   ::fe2c1238 Additional Data [W,N]  f5 4f 3f 3e 7e 22 d2 d9   (8 bytes ciphertext)
h567 Sony  5b833e05::5b833c14...eca4bd8f              "WH-CH720N"
```

Most Sony custom R chars return zero or empty when no app session is
active. The pattern is: Sony Headphones Connect protocol is
**bidirectional** — host writes a command opcode to a W char, the
peripheral responds via NOTIFICATION on the paired N char of the same
service. Without a write, the R chars remain idle.

The Fast Pair "Additional Data" (`f5 4f 3f 3e 7e 22 d2 d9`) is the
encrypted "Personalized Name" field per FP spec — needs the device's
Account Key (which lives only in the bonded user's Google account) to
decrypt.

The Sony app protocol char at h567 returns the Local Name string —
likely an "info / model identifier" attribute used by Headphones Connect
for product detection.

## Steps 3 + 4 — BLOCKED by firmware gap

Step 3 (read CCC descriptors) and step 4 (subscribe + correlate button
events) require **incoming notification handling**. Inspection of
`firmware/cc1352/src/att_client.c` shows zero handling for ATT opcodes
`0x1B` (HANDLE_VALUE_NTF) or `0x1D` (HANDLE_VALUE_IND). The firmware
GATT client implements READ + WRITE only.

Implications:
- Subscribing to a CCC has no effect from FeralRF's perspective —
  notifications hit the radio and get discarded.
- Bidirectional Sony protocol exploration (battery query, NC toggle
  echo, button press events) is not currently observable.
- This is a real firmware feature gap, not a configuration issue. Filing
  scope: ~1–2 sessions to add notification reception in `att_client.c`,
  define `RSP_GATT_NOTIFY` in `command_processor.c`, surface as async
  callback or pollable queue in `radio.py`.

## Step 5 — Airoha OTA service (deferred)

Service `fe59bfa87fe34a059d9499fadc69faff` at handles 144-156 is the
known Airoha OTA service. **Not probed.** Risk: bricking the headphones.
Only run with an intentional plan, an Airoha recovery path identified,
and explicit user authorization for the experiment.

## Firmware bug discovered: AttClient stale-state on second connect

Documented separately in `memory/project_gatt_attclient_bug.md`. After a
clean BLE GATT session + ble_disconnect, subsequent `ble_connect`
succeeds at LL but the peripheral never accepts the new CONNECT_IND
(verified by passive scan: peripheral keeps advertising during the
"connected" state). Master sends empty PDUs into the void, all ATT
operations time out silently. Workaround: `radio.reset_device(wait=2.5)`
before each GATT session.

## Skipped / informational

- (b) Sniffing during pairing — limited value. Sony WH-CH720N pairs via
  Bluetooth Classic (BR/EDR), not BLE; CC1352 has no BR/EDR sniffer.
- (d) ADV/SCAN_RSP capture & replay — adv is static, replay only spoofs
  device identity. Not a path to state knowledge. Useful later for clone
  experiments (F11b adjacent).
