## Verdict (from `_diagnose_nosync`)

> NO packets arrived in RX window across the entire loop — CONNECT_IND never lands inside the T_IFS=150µs window after slave's ADV_IND TX. Master timing too slow / master scanning other channels / master not actually attempting connection.

This rules out:
- AdvA mismatch (F20.a.1.d already confirmed sw-side match; HW counters now confirm filter behavior — no IGNORED counter increment ever)
- ChSel#2 (would show as `nRxIgnored > 0` since HW would RX the CONNECT_IND, parse it, then reject on filter mismatch)
- CRC errors (`nRxNok = 0`)
- RF setup failure on slave side (`nTxAdvInd = 200` proves slave RF chain works)

This confirms:
- Master's CONNECT_IND **never** lands inside slave's T_IFS=150µs RX window after the slave's ADV_IND TX. Either the master is too slow, on the wrong channel, or not actually sending CONNECT_IND.

Note: `f21_last_rssi = -94 dBm` is suspicious because no counter we accumulate (`nRxConnectReq/Ignored/Nok`) was non-zero — but the RSSI update guard ALSO includes `nRxScanReq`, which we did NOT accumulate. So a SCAN_REQ arrived from somewhere (likely an ambient BLE device on ch37) and bumped RSSI without touching our tracked counters. This is a gap in F20.a.1.e instrumentation worth fixing in F20.a.1.f (add `nRxScanReq` to the accumulators).

## Master side cross-check

Central reported (from `debug_conn_params`):
- `accessAddr=0xD9FF1979`, `hopInterval=24`, `supervTimeout=100`, `winOffset=8`, `hopIncrement=6`
- `connected: False`

So master DID compute a CONNECT_IND payload (the accessAddr/hopInterval/etc are valid prepared values), but the central reports `connected=False`. The most likely failure mode: master TX'd CONNECT_IND on ch37 → arrived at slave **after** slave's T_IFS window closed → slave never RX'd it → slave returns to ADV iteration → master never gets confirmation of slave joining the connection → master gives up after its initiator timeout (8s per F8d) → reports failure.

## F20.a.1.f Scope

The fix area is now narrow: **make master's CONNECT_IND land inside slave's T_IFS window**.

Candidate paths (cheapest first):

1. **Master scan settling** — ensure master's `CMD_BLE5_INITIATOR` is already in active RX on ch37 *before* slave begins TX'ing. Currently the smoke harness starts master after slave runs `advertise_ind()`. If master takes 100+ ms to enter active scan, it may miss the first ~10 slave ADV_INDs. Solution: start master initiator *first*, with a longer scan window, and *then* tell slave to begin advertising.

2. **Slave inter-iter `Task_sleep` analysis** — slave does `Task_sleep((interval - airtime)/1000 ms)` between iterations (10ms interval). The TI BLE patch's CMD_BLE_ADV opens RX for ~150µs after TX. If `Task_sleep` is invoked *during* that window, RTOS context switch could delay RX processing. Investigate `RadioIF_transmitBleAdvLegacy` loop timing.

3. **Slave's ADV_IND TX scheduling** — confirm slave uses `startTrigger.triggerType = TRIG_NOW` per iter (it does, per code review). The TI legacy ADV command should auto-open RX window without explicit gap. If there's a CPE patch issue affecting this, escalate.

4. **Add `nRxScanReq` to F21 accumulators** — small follow-up. The fact that `f21_last_rssi = -94` while all tracked counters are 0 means SCAN_REQ arrived but wasn't tracked. Worth fixing in passing.

Quickest reproduction-and-fix experiment: try path #1 — restructure the smoke harness so master starts scanning *before* slave begins advertising. If that works, F20.a.1.f is a Python-only fix to the harness order. Wire-level firmware behavior remains untouched.
