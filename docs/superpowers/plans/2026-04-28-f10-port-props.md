# F10 — Port props NoRTOS → TI-RTOS Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Validate that all 15 prop presets (GFSK / FSK / MSK / W-MBus / 4-FSK / 4-GFSK / OOK across 433/868/915/2440 MHz) work over-the-air on the TI-RTOS firmware line, ≥9/10 markers per preset, then tag `v2.0-f10`.

**Architecture:** Validation-pure. The full prop port (CMD_SET_PROP_CONFIG, band overrides, OOK genook patches, 433 SysConfig structs, format_conf for 4-FSK/4-GFSK, persistent 433 handle, RF_yield trick) is already in the source on `feature/f8a-ble-central-sniffle`. F10 flashes both boards, sweeps the OTA matrix, then commits a test marker per preset. Discipline: 1 preset = 1 commit, no batch.

**Tech Stack:** TI-RTOS 7, TI SimpleLink CC13xx/CC26xx SDK 8.30, CC1352P7, `feralrf` Python package, `smoke_ota_txrx.py`, `run_validation_baseline.sh`, catnip flasher, RP2040 reset shell.

## Failure handling — escalation rules

If during Tasks 4–19 a preset fails (`markers < 9/10`):

1. **First failure:** investigate immediately — check `RadioIF_setPropConfig` band branch, check the override table for that band/mod, check the `format_conf` path if it's a 4-FSK/4-GFSK preset. Fix, re-validate, commit `fix(f10): <preset> <root cause>` followed by the `test(f10): validate <preset>` commit.

2. **Second failure (different preset):** still fix per-preset.

3. **Third failure:** STOP. Do not continue per-preset. Escalate to the user with a summary of the three failures and ask whether to continue plan A or pivot to plan B (regression audit against `main` NoRTOS) per the spec §1 escalation rule.

For OOK preset failures specifically: check `s_prop_ook_active` lock path and `reset_device()` after OOK — likely a session lock issue, not an RF override.
